# SDD + TDD 四阶段闭环工作流 (SOP)

当用户调用此技能开启一个新功能或变更时，你必须严格按照以下**前置检查 + 四阶段有限状态机**顺序推进，**严禁跨阶段跳跃或绕过人工卡点**。

---

## 阶段 0：依赖与环境检查 (`0-preflight`)

在生成提案前必须完成以下检查；任一项失败都要停止，不得创建业务代码或测试代码。

1. **检查 OpenSpec CLI：** 在项目根目录执行 `command -v openspec`、`openspec version` 和 `openspec doctor`。确认命令存在、版本可读，且当前项目能被正确解析。
2. **检查 OpenSpec 项目结构：** 确认 `openspec/current/` 和 `openspec/changes/` 可用，并读取 `openspec/current/` 下的现有规范。若项目未初始化，向用户报告并建议运行 `openspec init`；不要通过创建空目录掩盖初始化失败。
3. **检查 OpenSpec 创建能力：** 执行 `openspec new change --help`，以当前安装版本支持的命令为准。不得假设 `openspec proposal` 或 `/openspec:proposal` 存在；只有实际可发现、可调用时才使用对应集成命令。
4. **检查 Superpowers：** 确认并实际调用以下 Skill：
   - `superpowers:subagent-driven-development`
   - `superpowers:test-driven-development`

   任一 Skill 不可用时，停止并告诉用户缺少哪项、它的用途以及安装后从哪个阶段继续。
5. **记录环境结果：** 报告 OpenSpec 版本、可用的 change 创建方式、项目语言/测试框架，以及两个 Superpowers Skill 均已可用。

---

## 阶段 1：蓝图契约 (`1-proposal`)

1. **读取规范：** 读取 `openspec/current/` 下的现有全局规范，避免与既有架构冲突。
2. **创建变更目录：** 根据当前 CLI 的帮助信息，使用实际可用的 `openspec new change <change-id>` 流程。`change-id` 仅使用小写字母、数字和连字符；创建后立即记录实际目录名，后续所有操作只使用这个已记录的 ID。
3. **生成变更文档：** 使用已发现的 OpenSpec 集成命令或当前版本的模板/指引，在 `openspec/changes/<change-id>/` 下生成并校验 `proposal.md`、`design.md` 和 `tasks.md`。用户需求不得直接拼接进未转义的 shell 命令；需要传参时使用工具的独立参数。
4. **边界锁定审查：** 在生成后主动向用户高亮总结以下三点：
   - **本次核心目标（In-Scope）**
   - **明确不做事项（Non-Goals / Out-of-Scope）**
   - **核心技术契约（接口、状态、窗口/尺寸约束等）**
5. **【强制卡点 Gate 1】** 停止执行，询问用户：*“提案与任务清单已生成，请确认边界是否准确（回复「确认」或给出修改意见）。”* 未获得明确同意前，绝对禁止编写任何业务或测试代码。

---

## 阶段 2：铁血施工 (`2-tdd-execute`)

收到用户对阶段 1 的确认后，必须实际调用 **Superpowers** 的 `subagent-driven-development` 与 `test-driven-development`，并按其规则落地代码：

1. **拓扑拆分批次：** 读取 `openspec/changes/<change-id>/design.md` 和 `tasks.md`，按依赖顺序拆分为适合本次变更的 1~4 个连贯小批次；小型或不可再拆分的变更允许只有 1 个批次，不得为了满足数量制造虚假任务。
2. **按项目技术栈执行验证：** 先识别项目语言、包管理器和测试框架，使用项目现有命令。不得默认 TypeScript、`.spec.ts` 或 `tsc --noEmit`。
3. **严格 Red-Green-Refactor：** 对核心逻辑（通信协议、JSON-RPC、Store、数据转换等）必须先写一个能复现需求的失败测试，确认红灯后编写最小实现使其变绿，再进行必要重构。配置或纯 UI 布局任务若没有合理的单元测试，则至少执行项目适用的类型检查、构建或静态验证，并记录验证命令。
4. **进度实时回写：** 每完成并验证通过一个子任务，立即在 `openspec/changes/<change-id>/tasks.md` 中将其对应的 `- [ ]` 更新为 `- [x]`。
5. **批次汇报与暂停：** 每完成一个批次，向用户简明汇报测试通过情况与变更文件列表，然后停止并等待用户明确回复“继续”。未收到“继续”前不得开始下一批次。
6. **最终全量验证：** 所有批次完成后，运行项目完整测试套件；对于没有单元测试的项目，运行其最接近的全量构建、类型检查或静态验证，并记录实际输出。只有全量验证通过，才能进入阶段 3。

---

## 阶段 3：人工联调验收 (`3-human-verify`)

当所有编码任务完成且最终项目级验证通过后：

1. **生成验收清单：** 对照 `proposal.md` 中的约定，向用户输出一份简短的本地验收指引（包含启动命令、核心交互检查项、边界条件检查项）。
2. **【强制卡点 Gate 2】** 挂起工作流，提示用户：*“所有代码与项目级验证已就绪，请在本地启动联调验收。验收通过后请回复「验收通过」以执行最终归档。”*

---

## 阶段 4：闭环归档 (`4-archive`)

收到用户的「验收通过」指令后：

1. **执行归档：** 使用前面记录的确切 `<change-id>`，运行当前版本支持的 `openspec archive <change-id>`，将本次变更的 Delta 规范合并至 `openspec/current/` 主规范中，并清理临时变更目录。
2. **归档后校验：** 确认归档命令成功，并再次运行 `openspec doctor` 或等效校验；失败时停止并报告，不得宣称归档完成。
3. **完结确认：** 确认归档成功后，向用户报告主规范已更新，整个开发闭环圆满结束。
